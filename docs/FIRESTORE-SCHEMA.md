> **สถานะ: ร่างทั้งหมด — ต้องยืนยันก่อน Implementation** (PD-11)

## Workflow คำขอใช้งาน (v1.2 — N-3, P-8, P-9)

| ขั้นตอน       | ผู้ทำ                    | สิ่งที่เกิดใน batch เดียวกัน                                                                                                                                                         |
| ----------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ยื่นคำขอ      | ผู้สมัคร (ตนเอง)          | สร้างคำขอ `status=pending` (บังคับ) · ห้ามมี `users/{uid}` อยู่แล้ว · ห้ามมีคำขอ pending ค้างอยู่                                                                                          |
| ปฏิเสธ       | SA/AD                  | `pending → rejected` + rejectedBy/rejectedAt + userAuditLogs E2 · คำขอที่ rejected แก้ไขหรือลบไม่ได้ (เป็นประวัติ)                                                                     |
| ยื่นใหม่ (P-9) | ผู้สมัคร (ตนเอง)          | สร้างคำขอ**ฉบับใหม่** `status=pending` (ฉบับก่อนหน้าต้องเป็น rejected) + userAuditLogs E15 · **ผู้ใช้เปลี่ยน status ของคำขอใด ๆ เองไม่ได้**                                                  |
| อนุมัติ (P-8)  | SA/AD (ตามขอบเขต role) | สร้าง `users/{uid}` `status=approved` + approvedBy/approvedAt + คัดลอก requestId/requestedRole/requestedAt + userAuditLogs E1 + **ลบคำขอที่ pending** (ข้อยกเว้นหลักห้ามลบ เฉพาะกรณีนี้) |

- ข้อยกเว้นการลบ (P-8) ใช้ได้เมื่อ Rules ยืนยันด้วย `getAfter()` ว่ามี `users/{uid}` สถานะ approved และ E1 ที่อ้างถึงใน batch เดียวกันเท่านั้น · ลบคำขอที่ rejected ไม่ได้
- ไม่คัดลอกข้อความอิสระ (`reason`, `reviewNote`) ไปยัง `users` (OI2-OB1 Pending)
- รายละเอียด Rules ยังเป็นข้อเสนอ — ต้องผ่าน Emulator Tests ก่อนใช้งาน

## requestId และความสัมพันธ์กับ E15 (v1.3 · ร่าง — ไม่เปลี่ยนมติ N-3, P-8, P-9)

| รายการ                 | ข้อกำหนด (ร่าง)                                                                                                                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `uid`                  | uid ของผู้ยื่น (`request.auth.uid`) · คำขอทุกฉบับของผู้ใช้คนเดียวกันมี `uid` เดียวกัน                                                                                                                                                    |
| `seq`                  | จำนวนเต็ม ≥ 1 · ฉบับแรก = 1 · ฉบับถัดไป = ฉบับก่อนหน้า + 1 · ไม่เติมเลขศูนย์ · ค่าสูงสุด **MAX_SEQ: P-10 Pending**                                                                                                                       |
| `requestId`            | Document ID = `uid + "_" + string(seq)` และต้องตรงกับ field `uid` / `seq` ทุกครั้ง (Rules ไม่แยกเลขจาก ID เอง เพื่อไม่พึ่งการ `split`)                                                                                                |
| ยื่นฉบับแรก (`seq = 1`)   | ต้องไม่มี `users/{uid}` · การบันทึก Audit ของคำขอฉบับแรก: **P-13 Pending** (เกี่ยวกับ OI2-OB2)                                                                                                                                      |
| ยื่นใหม่ (`seq ≥ 2`, P-9) | ฉบับ `{uid}_{seq−1}` ต้องมีอยู่และเป็น `rejected` · ต้องไม่มี `users/{uid}` · ระยะรอหลัง `rejectedAt`: **COOLDOWN: P-11 Pending** · ต้องสร้าง E15 ใน batch เดียวกัน                                                                      |
| E15 ↔ คำขอ             | ผูกกันสองทาง: คำขอ `seq ≥ 2` ต้องมี `userAuditLogs/accessRequests_{requestId}_v1` ใน batch เดียวกัน (`existsAfter`) และ E15 ต้องอ้างถึงคำขอที่ไม่มีอยู่ก่อน batch (`!exists`) แต่มีอยู่หลัง batch เป็น `pending` (`getAfter`) และ `uid` ตรงกับผู้ทำ |
| ผลที่ต้องได้               | มีคำขอ `pending` ได้ไม่เกิน 1 ฉบับต่อ `uid` · ไม่มี ID ซ้ำ (สร้างซ้ำ = update ซึ่งผู้สมัครทำไม่ได้) · ข้ามเลขไม่ได้                                                                                                                             |
| การยืนยันอีเมลของผู้ยื่น      | **P-15 Pending** (ความสัมพันธ์กับ K2)                                                                                                                                                                                          |

> ทั้งหมดเป็นข้อเสนอสำหรับเขียน Rules · รูปแบบ ID ยังต้องยืนยัน (**P-14 Pending**) · ต้องผ่าน Emulator Tests (EMULATOR-TEST-PLAN §7) ก่อนใช้งาน
